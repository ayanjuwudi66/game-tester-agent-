# 测试点拆分 Skill

## 功能概述
此skill将功能点进一步分解为具体的、可执行的测试点，为测试用例编写提供基础。

## 使用场景
在 `feature-splitter` skill完成功能点拆分后，调用此skill拆分测试点。

## 测试点定义
一个**测试点**是指：
- 针对功能点的一个具体验证角度
- 可以通过一个或多个测试用例来验证
- 具有明确的测试目标和验证标准

**重要**：测试点是抽象层级，一个测试点可对应多条测试用例。具体用例的场景展开由用例生成阶段完成。

## 🚨 输出格式速览（必读锚点）

**本 Skill 的唯一输出格式为六列 Markdown 表格**，任何其他格式（纯列表、编号列表等）均视为执行失败：

```
| 测试点ID | 功能点描述 | 测试点描述 | 主分类 | 适用分类 | 展开说明 |
```

- **ID格式**：`T{模块序号}.{子模块序号}.{序号}`（如 T1.2.3 = 模块 1 下第 2 个子模块的第 3 个测试点）
- **功能点描述**（第2列）：直接抄写 `功能点列表.md` 中所属子模块的「描述」字段；同一子模块下所有测试点该列内容相同。放在第2列便于下游生成器优先读取，符合"先功能点、后测试点"的阅读直觉
- **测试点描述**（第3列）：功能行为描述，不含分类词汇
- **适用分类**：至少标注2个分类标签，用逗号分隔
- **展开说明**：每条必须给出2-3个具体子方向，禁止笼统单词

> 📖 **ID 格式说明**详见 testcase-conventions skill · _shared_conventions.md §3。
> ID 用于定位测试点。功能点描述在第 2 列显式携带向下游，**不再依赖渲染层运行时反查**。

> ⚠️ 如果你的输出不是上述六列表格格式，**必须停止并重新生成**。详见步骤4。

## 执行流程

### 步骤1：接收功能点列表和归档信息
从 `feature-splitter` 的输出中获取功能点列表。
从 `file-scanner` 的输出中获取归档目录信息。

### 步骤2：测试点拆分策略

**核心原则：每个功能点必须从多个维度拆分，确保覆盖全面。**

#### 2.0 拆分前的维度检查（必做）

在拆分每个功能点前，先识别该功能点涉及哪些测试维度，**用于标注适用分类，而非为每个维度单独拆出测试点**：

```
功能点 → 维度检查（用于标注适用分类）
    ├── □ 核心流程（必有）→ 在适用分类中标注 HX
    ├── □ 非核心路径 → 在适用分类中标注 FHX
    ├── □ 边界条件（数值、长度、数量相关）→ 在适用分类中标注 BJ
    ├── □ 异常场景（网络、权限、竞态）→ 在适用分类中标注 YC
    ├── □ 中断恢复（操作中被中断）→ 在适用分类中标注 ZD
    └── □ 输入遍历（多种输入类型）→ 由用例生成阶段自动识别
```

**⚠️ 粒度自检规则**：如果你准备写出的测试点描述中包含"边界""异常""中断"等分类词汇，说明粒度过细——应该将其上提为功能行为描述，然后在适用分类中标注对应维度。

**⚠️⚠️ 重要澄清**：粒度自检**仅约束「测试点描述」列的文字表达**，不影响「适用分类」列的标注动作。即使测试点描述中不出现"边界""异常"等词，**适用分类列仍然必须标注所有适用维度**（如 BJ、YC、ZD 等）。"不为每个维度单独拆测试点" ≠ "不在适用分类列标注该维度"。

**强制要求**：至少从2个维度标注适用分类，避免只标出"HX"这类单一分类。

针对每个功能点，检查以下维度是否适用，**适用则标注到测试点的适用分类列**（而非为每个维度单独创建测试点）：

#### 2.1 核心功能维度（HX）— 判断是否适用
- 该测试点是否涉及功能的正常执行流程
- 该测试点是否涉及功能的正确输出结果
- 该测试点是否涉及用户必经的操作路径

#### 2.2 非核心功能维度（FHX）— 判断是否适用
- 该测试点是否涉及可选的功能路径
- 该测试点是否涉及非必须但重要的操作
- 该测试点是否涉及特定条件下才触发的功能

#### 2.3 边界值维度（BJ）— 判断是否适用

**核心规范：测试点描述必须包含具体数值**

| ❌ 错误做法 | ✅ 正确做法 |
|------------|------------|
| 验证密码位数边界 | 验证密码输入5位时的提示 |
| 验证列表数量上限 | 验证列表恰好8个时无滚动条 |
| 验证房间名长度限制 | 验证房间名超过10字显示截断 |

边界维度适用条件：
- 该测试点是否涉及最小值/最大值边界
- 该测试点是否涉及空值/空字符串处理
- 该测试点是否涉及数量限制边界（恰好达到、超过）

#### 2.4 异常场景维度（YC）— 判断是否适用
- 该测试点是否涉及网络异常（断网状态下操作）
- 该测试点是否涉及权限异常（无权限尝试操作）
- 该测试点是否涉及竞态条件（操作时数据已变更）
- 该测试点是否涉及敏感词/非法输入处理

#### 2.5 中断恢复维度（ZD）— 判断是否适用
- 该测试点是否涉及操作过程中网络断开再恢复
- 该测试点是否涉及操作过程中切换到其他应用再返回
- 该测试点是否涉及操作过程中被系统中断（来电等）

#### 2.6 状态/权限测试
- 不同用户权限下的表现
- 不同状态下的功能表现
- 状态流转的正确性

#### 2.7 通用测试维度（执行视角补充）

**即使需求文档未明确提及，以下维度也应主动检查是否适用：**

```
功能点 → 通用维度检查
    ├── □ 空值保存 → 输入为空时直接保存（BJ）
    ├── □ 敏感词过滤 → 输入敏感词时的处理（YC）
    ├── □ 特殊字符 → 输入特殊字符时的处理（BL/YC）
    ├── □ 默认状态优先 → 默认配置先于特殊配置测试（影响排序）
    ├── □ 首次/非首次 → 第一次操作 vs **非首次操作**（HX/FHX；注意"非首次"≠ FCG 的"反复"）
    └── □ 权限边界 → 无权限/权限过期时访问（YC）
```

**执行顺序考量**：测试点的排列顺序应考虑实际执行顺序。例如：
- 默认状态优先于特殊状态（如：公开房间 → 私密房间）
- 简单操作优先于复杂操作（如：查看列表 → 搜索列表 → 筛选列表）
- 正向流程优先于异常流程（如：正常创建 → 创建失败）

**在输出测试点列表时，按以上执行顺序排列，而非仅按分类排列。**

**空值保存检查**：任何涉及输入框、编辑、保存的功能点，都应考虑"不输入内容直接保存"场景。
**敏感词检查**：任何涉及用户输入文本的功能点（昵称、简介、评论等），都应考虑"输入敏感词"场景。

#### 2.8 对称性检查清单

**对于任何"正向操作"功能点，必须检查是否存在对称的"逆向操作"并为其生成测试点：**

| 正向操作 | 对称逆向操作 | 检查要点 |
|----------|-------------|----------|
| 创建/添加 | 删除/移除 | 删除后数据是否彻底清理 |
| 开启/启用 | 关闭/禁用 | 关闭后功能是否完全停止 |
| 加入/进入 | 退出/离开 | 退出后状态是否恢复 |
| 收藏/关注 | 取消收藏/取关 | 取消后列表是否同步更新 |
| 上架/发布 | 下架/撤回 | 下架后前端是否不可见 |
| 绑定/关联 | 解绑/取消关联 | 解绑后是否影响已有数据 |

**执行规则**：
- 逐一检查功能点列表中的每个操作，判断是否存在对称操作
- 如果对称操作在需求中**已明确描述** → 确认对应测试点已生成
- 如果对称操作在需求中**未提及但逻辑上应存在** → 标注【待确认】并生成测试点
- 如果对称操作**确实不适用**（如单向操作）→ 跳过并标注"不适用"

#### 2.9 通用兼容性维度清单

**以下兼容性维度应根据需求领域主动检查，适用则生成测试点：**

| 维度 | 适用场景 | 测试点方向 |
|------|----------|-----------|
| 多端同步 | 涉及多端（PC/移动/Web）使用的功能 | 一端操作后其他端是否同步 |
| 多角色视角 | 涉及多种用户角色的功能 | 不同角色看到的内容/权限差异 |
| 新旧版本兼容 | 有版本迭代的功能 | 旧版本数据在新版本中的表现 |
| 多语言/多时区 | 涉及国际化的功能 | 切换语言/时区后的显示和逻辑 |
| 横竖屏 | 移动端应用 | 横竖屏切换后布局和功能 |
| 大小屏适配 | 响应式设计的功能 | 不同分辨率下的显示和交互 |

**执行规则**：
- 非所有维度都需覆盖，根据需求领域判断适用性
- 适用的维度生成独立测试点，标注分类为 HX 或 FHX
- 不确定是否适用时标注【待确认】

#### 2.10 待确认需求强制落地规则

**对于上游标记为【待确认】的需求/功能点，在测试点拆分阶段必须处理，不得跳过：**

| 待确认类型 | 处理方式 | 测试点标注 |
|-----------|----------|-----------|
| 功能是否存在（如"可能有分享功能"） | 按"存在"假设生成测试点 | 测试点描述后追加【待确认：功能是否存在】 |
| 具体逻辑不明确（如"搜索支持模糊匹配？"） | 按最常见实现生成测试点 | 测试点描述后追加【待确认：具体逻辑】 |
| 数值未明确（如"列表上限未说明"） | 按行业常见值假设（如20条/页） | 测试点描述后追加【待确认：具体数值=假设值】 |

**强制要求**：
- 所有【待确认】项都必须产生至少1个测试点
- 测试点中的假设值必须明确标注，便于后续确认后修改
- 禁止因为"不确定"就不生成测试点

#### 2.11 配置表字段强制扫描（需求含配置表时必做）

**触发条件**：当需求文档中包含配置表、字段定义表、数据结构表时，必须执行本步骤。

**扫描规则**：逐一检查配置表中的每个字段，识别可测试的边界和异常方向，并在相关测试点的「适用分类」和「展开说明」中体现：

| 字段类型 | 识别特征 | 应标注分类 | 展开说明方向 |
|----------|---------|-----------|-------------|
| 必填字段 | 标注"必填"、"required"、"不可为空" | BJ | 缺失/空值时的容错 |
| 数值字段 | 整数、浮点、金额、数量、次数 | BJ | 0值/负值/极大值/类型错误(如传字符串) |
| ID/关联字段 | xxxId、关联ID、外键 | BJ,YC | 关联记录不存在/已删除时的处理 |
| 时间字段 | 日期、时间、开始时间、结束时间 | BJ | 非法日期/空值/格式异常/时间逆序 |
| 枚举字段 | 类型、状态、选项（有限值域） | BJ | 无效枚举值/越界值/未定义值 |
| 百分比/比例 | 折扣、比例、占比 | BJ | 0%/100%/超限/负值/精度 |
| 字符串字段 | 名称、描述、备注 | BJ,BL | 空串/超长/特殊字符/富文本标签 |

**输出要求**：扫描结果直接体现在测试点的「展开说明」列中，格式如：`BJ:必填字段缺失/数值为0/ID不存在/日期非法`

### 🚫 UI测试点排除规则

**以下内容不需要拆分为测试点，应由UI走查覆盖：**

| 排除类型 | 示例 | 原因 |
|----------|------|------|
| 精确像素尺寸 | "按钮90×28px"、"弹窗560×840px" | UI走查覆盖，变动频繁 |
| 精确颜色值 | "rgba(0,0,0,0.3)"、"#8477FF" | UI走查覆盖 |
| 字号大小 | "12px字号"、"24px标题" | UI走查覆盖 |
| 圆角/间距 | "圆角16px"、"间距12px" | UI走查覆盖 |
| 纯视觉样式 | "灰色文字"、"渐变背景" | UI走查覆盖 |
| 动画细节 | "0.3s渐入动画" | UI走查覆盖 |

**✅ 应该测试的UI相关内容：**

| 测试类型 | 示例 | 原因 |
|----------|------|------|
| 元素可见性 | "按钮是否显示" | 功能可用性 |
| 元素可交互 | "按钮可点击" | 功能正确性 |
| 状态切换 | "禁用/启用状态" | 业务逻辑 |
| 数据正确性 | "金额显示正确" | 数据一致性 |
| 功能响应 | "点击后跳转" | 功能完整性 |

### 步骤3：测试点多维度分类标注

**🚨 核心改动：每个测试点必须标注所有适用的分类，而非只标一个！**

**问题说明**：旧方案中每个测试点只标一个分类（如"HX"），导致该测试点只生成对应分类的用例，其他维度的用例缺失。例如"验证创建房间功能"如果只标HX，就不会生成BJ/YC/ZD用例。

**新方案**：每个测试点标注「主分类」+「适用分类」，明确该测试点需要哪些类型的用例覆盖。

#### 3.1 分类标签定义

| 标签 | 含义 | 对应用例生成 Skill |
|------|------|-------------------|
| HX | 核心功能 | testcase-core |
| FHX | 非核心功能 | testcase-core |
| BJ | 边界场景 | testcase-boundary |
| YC | 异常操作 | testcase-exception |
| ZD | 中断恢复 | testcase-interrupt |
| BL | 功能遍历 | testcase-traverse |

#### 3.2 适用分类判定规则

**每个测试点在标注时，必须逐一检查以下适用条件：**

| 分类 | 适用条件（满足任一即适用） | 示例 |
|------|--------------------------|------|
| HX | 所有核心功能测试点（必有） | 验证创建房间 → HX适用 |
| FHX | 有可选路径、非必经操作 | 已在房间内时创建 → FHX适用 |
| BJ | 涉及输入框、列表数量、数值范围、长度限制 | 有输入框 → BJ适用 |
| YC | 涉及网络请求、用户操作、权限、并发 | 有网络请求 → YC适用 |
| ZD | 涉及异步操作、加载过程、网络请求 | 有加载过程 → ZD适用 |
| BL | 涉及输入框（多种输入类型）、选项切换、搜索 | 有输入框 → BL适用 |

**典型测试点的多分类标注示例：**

| 测试点 | 适用分类 | 标注说明 |
|--------|---------|---------|
| 验证创建房间功能 | HX,FHX,BJ,YC,FCG,ZD,BL | 有输入框(BJ/BL)、有网络请求(YC/ZD)、有可选路径(FHX) |
| 验证房间列表展示 | HX,BJ,YC | 有列表数量边界(BJ)、有网络请求(YC) |
| 验证联机入口显示 | HX | 纯展示无交互，仅HX |
| 验证房间名编辑功能 | HX,BJ,YC,ZD,BL | 有输入框(BJ/BL)、有保存操作(YC/ZD) |
| 验证密码输入功能 | HX,BJ,BL | 有输入框(BJ/BL)、6位密码(BJ) |

**强制要求**：
- 每个测试点的适用分类**至少包含HX**（因为HX是核心正向验证）
- 涉及输入框的测试点**必须包含BJ和BL**
- 涉及网络请求的测试点**必须包含YC**
- 涉及异步操作/加载的测试点**必须包含ZD**
- 适用分类 ≠ 必须生成用例的分类，但标注了则后续skill必须覆盖

### 3.3 展开说明的质量指导

**展开说明是后续用例生成 Skill 展开用例的核心线索，质量直接影响用例覆盖充分性。**

**质量标准**：展开说明应点出关键变化维度或子场景方向，让用例生成 Skill 知道"往哪些方向展开"。

**质量等级示例**：

| 等级 | 示例 | 问题 |
|------|------|------|
| 🔴 差 | `BJ:边界` | 太笼统，无法指导展开方向 |
| 🟡 一般 | `BJ:房间名边界` | 指出了对象，但缺少维度提示 |
| 🟢 好 | `BJ:房间名空值/临界/超限` | 点出具体维度，便于逐一展开 |
| 🔴 差 | `YC:异常` | 无任何线索 |
| 🟡 一般 | `YC:网络异常` | 指出大类，但可细分 |
| 🟢 好 | `YC:断网操作/弱网加载/请求超时` | 给出子场景方向 |

**撰写要求**：
- 不需要穷举所有细节用例，但要给出**方向性线索**
- 多个维度/子场景用 `/` 分隔
- 避免过于笼统的单词（如"正常"/"边界"/"异常"/"遍历"）
- 尽量点出 2-3 个具体子方向

### 步骤4：输出格式规范（唯一格式 + 门控约束）

**🚨🚨🚨 格式门控（阻断性）：输出必须为六列 Markdown 表格。如果输出为纯列表、编号列表或其他非表格格式，视为执行失败，必须停止并重新生成。**

#### 4.1 唯一输出格式

测试点**只允许**使用以下六列表格格式输出：

```
| 测试点ID | 功能点描述 | 测试点描述 | 主分类 | 适用分类 | 展开说明 |
|:--------:|-----------|-----------|:------:|:--------:|----------|
```

- **测试点ID**：格式为 `T{模块序号}.{子模块序号}.{序号}`（如 T1.2.3 = 模块 1 下第 2 个子模块的第 3 个测试点）
  - 模块序号：对应 `功能点列表.md` 中的一级模块编号
  - 子模块序号：对应该模块下的子模块编号（feature-splitter 输出的 `1.1 / 1.2 / 1.3` 中的第二段数字）
  - 序号：该子模块下的测试点连续编号（1、2、3...）
- **功能点描述**（第2列）：该测试点所属子模块的功能说明
  - **来源**：直接抄写 `功能点列表.md` 中对应子模块的 `- **描述**:` 字段值
  - **规则**：同一子模块下所有测试点该列内容完全相同（因为同属一个功能点）
  - **用途**：下游 5 个 testcase-* 生成器读取此列，写入 JSONL 的 `feature_point` 字段（生成阶段静态传递，渲染层无需反查）
  - **缺失兜底**：若 `功能点列表.md` 中该子模块缺「描述」字段，本列填写子模块名（禁止留空）
- **测试点描述**（第3列）：功能行为描述，不含分类词汇（"边界""异常""中断"等）
- **主分类**：该测试点最核心的分类（HX/FHX/BJ/YC/FCG/ZD/BL 之一）
- **适用分类**：所有适用的分类标签，逗号分隔，**至少2个**；涉及可点击元素 / 前置动画·加载·结算 / 可反复进入退出的状态 / 多入口或需按顺序多步操作时，**应含 `FCG`**
- **展开说明**：各分类对应的展开方向，格式为 `分类:方向1/方向2/方向3`，分号分隔多个分类

#### 4.2 展开说明列撰写规范

展开说明是后续用例生成 Skill 展开用例的**核心线索**，质量直接影响用例覆盖充分性。

**格式**：`HX:方向; BJ:方向; YC:方向`（按适用分类逐一给出展开方向）

**质量等级**：

| 等级 | 示例 | 问题 |
|------|------|------|
| 🔴 差 | `BJ:边界` | 太笼统，无法指导展开 |
| 🟡 一般 | `BJ:房间名边界` | 有对象，缺维度提示 |
| 🟢 好 | `BJ:房间名空值/临界/超限` | 点出具体维度 |
| 🔴 差 | `YC:异常` | 无任何线索 |
| 🟢 好 | `YC:断网操作/弱网加载/请求超时` | 给出子场景方向 |

**撰写要求**：
- 每个适用分类都必须有对应的展开说明
- 多个维度/子场景用 `/` 分隔
- 避免过于笼统的单词（"正常"/"边界"/"异常"/"遍历"）
- 每个分类尽量给出 2-3 个具体子方向

## 拆分原则

### 1. MECE原则
- 相互独立（Mutually Exclusive）
- 完全穷尽（Collectively Exhaustive）

### 2. 测试金字塔原则
- P0测试点应该覆盖核心功能
- P1测试点覆盖重要业务场景
- P2测试点覆盖边缘情况

### 3. 风险导向原则
- 高风险功能分配更多测试点
- 关注历史问题多发区域

### 4. 可执行原则
- 测试点必须可以转化为具体测试用例
- 避免过于抽象的测试点

## 测试点数量建议
- 简单功能点：3-5个测试点
- 中等功能点：5-10个测试点
- 复杂功能点：10-15个测试点

## 检查清单

### 🚨 格式门控（阻断性 — 不满足则必须重新生成）

```
□ 输出是否为六列 Markdown 表格（测试点ID | 功能点描述 | 测试点描述 | 主分类 | 适用分类 | 展开说明）？ → 否则停止，重新生成
□ 测试点ID是否为 T{模块序号}.{子模块序号}.{序号} 三段格式（如 T1.2.3）？ → 否则修正
□ ID 中的模块/子模块序号是否与 功能点列表.md 中的编号一致？ → 不一致则修正
□ 每行的「展开说明」列是否非空？ → 为空则补充后再输出
□ 每行的「适用分类」列是否至少包含2个标签？ → 不足则回溯补充
□ 🚨 每行的「功能点描述」列是否非空，且与 功能点列表.md 中对应子模块的「描述」字段一致？ → 缺失/不一致则修正
□ 🚨 分类统计表和覆盖率表是否已输出？ → 未输出则补充
□ 🚨 多分类覆盖率是否 ≥60%？ → 不满足则回溯补充分类标注
```

### ✅ 质量检查（建议性 — 尽量满足）

```
□ 每个功能点至少有 HX（核心功能）测试点
□ 涉及数值/长度/数量的功能点有 BJ（边界）测试点
□ 涉及网络操作的功能点有 ZD（中断恢复）测试点
□ 边界类测试点描述包含具体数值（如"8个"而非"上限"）
□ 粒度自检：测试点描述中不包含"边界""异常""中断"等分类词汇（如果包含，说明粒度过细，应上提为功能行为描述）
□ 每个测试点的「适用分类」已逐项检查，涉及输入框必含BJ和BL，涉及网络请求必含YC，涉及异步操作必含ZD
□ 展开说明列非笼统单词，每条给出2-3个具体子方向（如"BJ:空值/临界/超限"而非"BJ:边界"）
```
