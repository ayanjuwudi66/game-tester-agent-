# 测试用例生成调度器

> **本 Skill 为纯调度器**，负责按顺序调度子 Skill，并在最终聚合前执行覆盖率检查。
> 具体的格式规范（表头 profile / 逻辑字段 / 功能点描述传递链路 / 分类定义 / 撰写规范 / 编码 / 路径）均由独立 skill
> `testcase-conventions` 承载：testcase-conventions skill · _shared_conventions.md，本 Skill 不重复。

---

## 子 Skill 清单

| 子 Skill | 职责 | 生成分类 |
|----------|------|----------|
| `testcase-core` | 核心用例生成 | HX, FHX |
| `testcase-boundary` | 边界场景用例 | BJ |
| `testcase-exception` | 异常操作用例 | YC |
| `testcase-traverse` | 功能遍历用例 | BL |
| `testcase-interrupt` | 中断场景用例 | ZD |
| `testcase-aggregator` | 聚合排序输出CSV | - |

---

## 调度流程（按模块纵切）

> ⚠️ **模式变更说明**：原"按分类横切"模式已废弃。现采用"按模块纵切"模式：
> **对模块A 依次跑完 HX→FHX→BJ→YC→FCG→BL→ZD 全部分类，每个 skill append 到 A.jsonl，再进入模块B**。
> CSV 由末尾 aggregator 一次生成（就地调用 run_pipeline.py），不再增量写入。

```
测试点列表（按模块分组）
    │
    ▼（步骤0：通用组件识别）
    │
    ╔══════════════════════════════════════════╗
    ║  外层循环：逐模块处理                      ║
    ║                                          ║
    ║  模块X 的测试点                           ║
    ║      │                                   ║
    ║      ▼ ① testcase-core (HX + FHX)       ║
    ║      ▼ ② testcase-boundary (BJ)         ║
    ║      ▼ ③ testcase-exception (YC)        ║
    ║      ▼ ④ testcase-traverse (BL)         ║
    ║      ▼ ⑤ testcase-interrupt (ZD)        ║
    ║      │  (5 个 skill 各自 append 到      ║
    ║      │   测试用例_模块/{模块}.jsonl)      ║
    ║      ▼ ⑥ 更新 temp/_progress.json        ║
    ║                                          ║
    ╚══════════════════════════════════════════╝
    │
    ▼（所有模块完成后）
[覆盖率检查 + 展开充分性检查]（步骤6）
    │
    ▼（步骤7）
testcase-aggregator → 就地调用 run_pipeline.py →
    md2csv 输出 CSV + stats.json / validate 输出 report.json
```

> 🚨 **关键约束**：同一模块内各分类**必须顺序执行**（后续分类可参考前序分类用例避免重复）。不同模块之间顺序执行。

## 步骤0：通用组件识别（调度前执行）

扫描测试点，识别涉及通用UI组件，读取对应参考用例：

| 组件类型 | 识别关键词 | 参考文件 |
|----------|------------|----------|
| 文字输入框 | 输入框、搜索框、密码、房间名 | `references/文字输入框通用用例.md` |

---

## 步骤1-5：按模块循环调度子生成器

**对每个模块**，依次调用以下子 Skill（每次只传入**当前模块**的测试点）：

1. `testcase-core` → 生成 HX / FHX 用例
2. `testcase-boundary` → 生成 BJ 用例
3. `testcase-exception` → 生成 YC 用例
4. `testcase-traverse` → 生成 BL 用例
5. `testcase-interrupt` → 生成 ZD 用例

**单模块完成后**：
- 每个生成器 skill 都已用 `open(mode='a')` 将自己产出的分类用例追加到 `测试用例_模块/{模块名}.jsonl`
- **不再有独立的 write_to_file 一次性写出步骤**（旧模式产物已废弃）
- **不再有增量追加 CSV 步骤**（CSV 由 aggregator 一次生成）
- 更新 `temp/_progress.json` 标记该模块为已完成

> 💡 如果中途中断，从 `temp/_progress.json` 中读取已完成模块列表，跳过已完成模块，从断点处继续。

---

## 步骤6：🚨🚨🚨 硬性门控检查（阻断性，不通过则禁止执行步骤7）

**在调用 testcase-aggregator 前，必须通过以下两项门控检查！任一不通过则禁止执行步骤7，必须回溯补充。**

### 门控1：测试点-分类覆盖率 ≥ 90%

**操作方法**：
1. 读取测试点列表的「适用分类」列，提取每个测试点需要覆盖的分类
2. 读取所有已生成的 JSONL 用例文件，统计每个测试点实际覆盖分类
3. 对比发现缺失

> ⚠️ **统计口径：`FCG` 不参与本门控。** 一个测试点只要**除 FCG 之外**的适用分类都出了用例，即计入「已全覆盖」。FCG 属**建议层**（触发条件命中就该出，缺席**不阻断、不回溯**）。

**覆盖率报告格式：**
```
📊 测试点-分类覆盖率检查
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
测试点总数：{N}
已全覆盖：{M} ({M/N*100}%)
有缺失：{K}

缺失详情：
| 测试点 | 适用分类 | 实际覆盖 | 缺失分类 |
|--------|---------|---------|---------|
| 验证创建房间 | HX,FHX,BJ,YC,FCG,ZD,BL | HX,FHX | BJ,YC,ZD,BL |
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

**🚨 阻断规则**：
- 覆盖率 ≥ 90% → ✅ 通过，继续检查门控2
- 覆盖率 < 90% → ❌ 阻断！回溯对应子 Skill 补充缺失分类的用例后重新检查

### 门控2：最低用例数 ≥ 测试点数 × 2.5

**🚨 阻断规则**：
- 总用例数 ≥ 测试点数 × 2.5 → ✅ 通过，执行步骤7
- 总用例数 < 测试点数 × 2.5 → ❌ 阻断！回溯展开不足的 Skill 补充用例后重新检查

**回溯优先级**（用例数不足时按此顺序补充，具体阈值见`_shared_conventions.md §11`）：
1. 检查 HX 用例：非纯展示型测试点是否都有 ≥2 条用例（参见 §11.1）→ 不足则回溯 testcase-core
2. 检查 BJ 用例：涉及输入框/数值的测试点是否都有 ≥3 条用例（参见 §11.1）→ 不足则回溯 testcase-boundary
3. 检查 YC 用例：涉及网络请求的测试点是否都有 ≥2 条用例（参见 §11.2）→ 不足则回溯 testcase-exception
4. 检查 BL/ZD 用例：展开说明暗示多种子场景但只有1条用例（参见 §11.2）→ 回溯对应 Skill

---

## 步骤6.5：展开充分性检查（强制）

遍历每个测试点，若某分类下只有1条用例且展开说明含多个子场景（用"/"分隔），标记为"展开可能不足"。

**处理策略**：
- 标记 ≤ 5 → 回溯对应 Skill 补充用例
- 标记 > 5 → 报出警告列表，由用户决定

---

## 步骤7：调用 testcase-aggregator

调用聚合器完成排序和 CSV 生成。

---

## 质量基准

```
最低用例数 = 测试点数量 × 2.5
平均展开率 = 总用例数 / 测试点数 ≥ 2.0
测试点-分类覆盖率 ≥ 90%
```

| 分类 | 最低占比 |
|------|----------|
| HX | 30% |
| BJ | 15% |
| YC | 10% |
| BL | 8% |
| ZD | 4% |
