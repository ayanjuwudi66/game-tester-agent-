# 需求整理 Skill

## 功能概述
此skill将多模态解析后的原始内容进行整理、归纳和结构化，提炼出清晰的需求描述文档。

## 使用场景
在 `multimodal-parser` skill完成文件解析后，调用此skill整理需求内容。

---

## ⚠️ 整理核心原则（强制遵守）

### 原则1：需求来源分类

需求按来源分为三类，处理方式不同：

| 来源类型 | 定义 | 处理方式 | 输出标记 |
|----------|------|----------|----------|
| **确定需求** | 图片可见UI元素 + OCR明确文字 | 直接整理为需求 | 无标记 |
| **待确认需求** | 基于可见元素的合理推断（上游标记【待确认】） | 整理但保留标记 | 【待确认】 |
| **不确定需求** | 上游标记 [?] 或 [无法识别] | 放入待确认区域 | [?] |

```
✅ 确定需求示例：
- [图片] 页面有搜索输入框 → "搜索功能"（确定需求）
- [图片OCR] 按钮文案"创建房间" → "创建房间功能"（确定需求）

⚠️ 待确认需求示例：
- [图片推断] 搜索框支持模糊搜索【待确认】 → "模糊搜索功能【待确认】"
- [图片推断] 密码输入框支持显示/隐藏切换【待确认】 → "密码显隐切换【待确认】"

❌ 不确定需求示例：
- [?] 可能是分享按钮 → 放入"待确认需求"区域
```

### 原则2：原文溯源（每个需求点必须有依据）

每个提取的功能点/需求点必须：
1. 能在原始解析内容中找到明确依据（可见元素或文字说明）
2. 标注依据的来源位置

**溯源格式**：
```markdown
| 需求点 | 原文依据 | 来源 | 状态 |
|--------|----------|------|------|
| 搜索房间功能 | 房间列表顶部有搜索输入框 | [图片] 图02 | 确定 |
| 房间密码设置 | 创建房间弹窗中有密码输入框 | [图片] 图02 | 确定 |
| 模糊搜索功能 | 搜索框支持模糊搜索【待确认】 | [图片推断] | 待确认 |
```

### 原则3：【待确认】内容保留但标记

对于来自上游的推断内容：

| 上游标记 | 处理方式 |
|----------|----------|
| `【待确认】` | 保留标记，正常整理为需求，但在功能列表中显示【待确认】 |
| `[?]` | 保留标记，放入"待确认需求"区域 |
| `[无法识别]` | 保留标记，放入"待确认需求"区域 |
| 无标记 | 正常整理为确定需求 |

**输出时区分**：
- **确定需求**：有明确UI元素或文字依据
- **待确认需求**：基于推断或信息不完整
- **不确定需求**：来源标记为 [?] 或 [无法识别]

### 原则4：可见UI元素即为有效依据

**重要：图片中可见的UI控件本身就是有效的需求依据，不需要额外的文字说明。**

```
✅ 有效依据：
- 看到搜索框 → 搜索功能是确定需求
- 看到密码输入框 → 密码设置是确定需求
- 看到刷新按钮 → 刷新功能是确定需求

⚠️ 需标记【待确认】：
- 搜索框的具体搜索逻辑（模糊/精确）
- 密码的具体规则（长度、复杂度）
- 刷新的具体行为（手动/自动）
```

### 原则5：禁止凭空推断

以下情况**禁止**：

```
❌ 图片中完全看不到任何相关元素，却添加功能
❌ 没有任何UI线索，仅凭"应该有"添加功能
```

**强制规则：无证据 = 只能走 `[建议补充]`**

凡不能在原文（文字/图片UI元素）中指出直接证据的功能，**禁止**作为确定需求或待确认需求输出，只能使用 `[建议补充]` 标签放入第八章待确认清单。禁止以"业界标准""行业惯例""通用做法"等自创理由将其升级为需求。

如果确实需要补充建议，必须明确标注：
```markdown
[建议补充] 此处原文未提及，建议与产品确认是否需要：xxx
```

### 原则6：自包含性原则（最高优先级）

**需求整理报告必须具备自包含性：后续AI仅参考此文档即可重新生成完整测试用例，无需回看原始需求文档。**

这意味着：
- 所有影响测试的信息都必须在报告中体现，不得依赖"去看原始需求"
- 用户体验流程图（第三章末尾子节）和配置表数据（第四章）是自包含性的关键组成部分，**必须输出**
- 如果某项信息在原始需求中存在但报告中缺失，则报告不合格

## 执行流程

### 步骤1：接收解析内容和归档信息
从 `multimodal-parser` 的输出中获取解析后的文档内容。
从 `file-scanner` 的输出中获取归档目录信息。

### 步骤2：识别需求类型
分析内容，识别需求类型：
- **功能需求**: 系统需要实现的功能
- **业务规则**: 业务逻辑和约束条件
- **界面需求**: UI/UX相关的描述
- **数据需求**: 数据格式、存储、展示要求
- **性能需求**: 性能指标和约束
- **兼容性需求**: 平台、设备兼容要求

### 步骤3：提取关键信息
从文档中提取以下关键信息：

#### 3.1 项目基本信息
- 项目/功能名称
- 版本/迭代信息
- 相关模块

#### 3.2 需求背景
- 需求来源
- 业务目标
- 用户场景

#### 3.3 功能描述
- 功能入口
- 操作流程
- 交互说明

#### 3.4 业务规则
- 数据规则
- 显示规则
- 计算逻辑

#### 3.5 图片内容深度解析（重要！）

**图片是需求的重要信息来源，必须逐张、逐区域深度解析，防止遗漏。**

##### 3.5.1 图片解析流程

```
对于每张图片：
    1. 整体浏览 → 识别页面/弹窗/组件类型
    2. 分区扫描 → 按区域（顶部/中部/底部/左侧/右侧）逐一识别
    3. 元素提取 → 识别每个区域内的所有UI元素
    4. 状态记录 → 记录元素的状态、文案、样式特征
    5. 交互标注 → 识别需求文档中描述的交互行为（如"3s后消失"）
```

##### 3.5.2 图片分区扫描要点

| 区域 | 常见元素 | 易遗漏点 |
|------|----------|----------|
| 顶部导航栏 | 返回按钮、标题、右侧操作按钮 | 状态指示图标、小红点 |
| 页面主体 | 列表、卡片、表单 | 空状态、加载状态 |
| 底部区域 | 操作按钮、Tab栏 | 安全区适配、按钮状态 |
| 弹窗/浮层 | 弹窗内容、按钮 | 遮罩层、关闭方式、动画 |
| 边栏/抽屉 | 侧边栏内容 | 展开/收起触发方式 |
| 角落/边缘 | 状态标签、角标 | 小图标、状态指示器 |

##### 3.5.3 必须关注的元素类型

| 类型 | 识别要点 | 常见遗漏 |
|------|----------|----------|
| 按钮 | 所有可点击区域 | 禁用状态按钮、图标按钮 |
| 状态指示 | 图标颜色/形状变化 | 在线/离线状态、进度指示 |
| 时间反馈 | 气泡/Toast/提示 | 显示时长（如"3s后消失"） |
| 输入区域 | 输入框/搜索框 | placeholder、字数限制 |
| 列表/卡片 | 列表项内容结构 | 空列表状态、加载更多 |

#### 3.6 UI元素提取清单

**从图片和文档中提取所有UI元素，确保不遗漏：**

| 元素类型 | 提取要点 | 需记录的状态 |
|----------|----------|--------------|
| 按钮/入口 | 按钮文案、位置 | 正常/禁用/加载中/选中 |
| 状态指示器 | 图标、颜色、含义 | 各状态的视觉差异 |
| 弹窗/对话框 | 触发条件、内容、按钮 | 显示/隐藏条件 |
| Toast/气泡 | 内容、位置 | 显示时长（秒） |
| 输入框 | 位置、用途 | placeholder、限制条件 |
| 下拉框/选择器 | 选项内容 | 默认值、展开状态 |
| 列表 | 列表项结构 | 空状态、加载状态 |
| 侧边栏/抽屉 | 展示内容 | 展开/收起条件 |
| 导航栏/Tab | Tab项 | 切换逻辑、选中状态 |
| 角标/标签 | 位置、内容 | 显示条件 |

**输出清单格式**：
```markdown
### UI元素清单

| 序号 | 元素类型 | 元素名称 | 位置描述 | 状态/行为 | 来源图片 | 备注 |
|------|----------|----------|----------|-----------|----------|------|
| 1 | {类型} | {名称} | {位置} | {状态描述} | 图{N} | {备注} |
```

**重要**：`来源图片`字段用于追溯，确保每个元素都有明确的出处。

#### 3.7 交互反馈提取清单

**识别所有带时间参数的交互反馈，这是最容易遗漏的部分：**

| 反馈类型 | 提取要点 | 关注的参数 |
|----------|----------|------------|
| 延时反馈 | Toast/气泡提示 | 显示时长（如3s） |
| 自动消失 | 提示信息消失 | 消失时间 |
| 动画效果 | 过渡动画 | 动画时长 |
| 状态切换 | 按钮/图标变化 | 触发条件 |
| 自动行为 | 定时操作 | 触发时间/条件 |
| 加载反馈 | 加载指示器 | 超时时间 |

**输出清单格式**：
```markdown
### 交互反馈清单

| 序号 | 反馈类型 | 触发条件 | 反馈内容 | 时间参数 | 来源 |
|------|----------|----------|----------|----------|------|
| 1 | {类型} | {条件} | {内容} | {时间} | 文档/图{N} |
```

### 步骤4：需求结构化输出
将整理后的需求以标准格式输出（共9章，每章均为 🚨**强制输出**，不可跳过）：

```markdown
## 需求整理报告

> ⚠️ **自包含性自检**：本报告应包含重新生成完整测试用例所需的全部信息，后续AI仅参考此文档即可工作，无需原始需求文档。请确认：用户体验流程图已输出、配置表数据（如有）已完整输出、测试维度补充已覆盖。

---

### 一、需求概述

| 开放周期 | {功能的时间约束，如"长期"/"活动期间"} |
```

{需求名称}

│   ├── {二级功能A1}

```
> - 每个叶子节点对应第三章中的一个功能点
> - 如功能点是推断得来的，在末尾标注 `【推断】`
```

```
### 四、配置表数据

🚨 **强制输出**：如果需求中涉及任何配置项，必须完整输出字段定义和示例数据行。如无配置项则标注"本需求无配置字段"。

#### 4.1 {表名1}（如：商店表）

**字段定义：**
```
