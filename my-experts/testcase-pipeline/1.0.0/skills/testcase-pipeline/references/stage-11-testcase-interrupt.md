# 中断场景用例生成 Skill

## 🚨 前置步骤（必须最先执行）

**在生成任何用例之前，必须加载共享规范 skill：**

```
use_skill: testcase-conventions
# 加载后按 SKILL.md §二加载策略读取（弱基座回落）
read_file: references/_shared_conventions.md
```

该文件包含：8列格式规范、分类定义、6条撰写规范、UI排除规则、数值具体化规范、追加工具约束。**以下所有步骤均在遵守共享规范的前提下执行。**

---

## 🚨 最高优先级约束

**本 Skill 只负责生成 ZD（中断/重连）分类的测试用例。**

- ✅ 允许的分类：ZD
- ❌ 禁止的分类：HX、FHX、BL、BJ、YC、FCG（这些由其他 Skill 负责）

---

## ⚠️ 重要区分：ZD vs YC

| 场景 | 分类 | 说明 |
|------|------|------|
| 断网状态下点击按钮 | **YC** | 操作前已断网，属于异常状态下的操作 |
| 操作过程中网络断开再恢复 | **ZD** | 操作中途被中断，然后恢复 |
| 弱网环境下操作 | **YC** | 网络不稳定，但未完全断开 |
| 操作过程中杀进程再启动 | **ZD** | 进程中断后重新启动 |
| 操作跨越时间边界（如跨天/跨活动周期） | **ZD** | 操作期间时间条件发生变化 |
| 持续弱网导致操作超时后重试 | **ZD** | 弱网持续时间超过阈值触发超时中断 |

---

## 核心原则：聚焦操作被中断后的恢复能力

```
示例：测试点「验证加入房间中断恢复」→ 展开为多条 ZD 用例：
├─ 用例1：加入过程中断网后恢复
├─ 用例2：加入过程中切后台后恢复
├─ 用例3：加入过程中来电后恢复
└─ 用例4：加入过程中锁屏后恢复
```

## 执行流程

### 步骤1：读取测试点五列表格（强制）

从测试点列表的「适用分类」列筛选含 ZD 的测试点，**这些测试点必须生成 ZD 用例**。同时读取「展开说明」列获取 ZD 展开线索。

**🚨 降级展开逻辑（当展开说明缺失或笼统时）**：

如果某测试点的「展开说明」中 ZD 部分为空或过于笼统（如仅写"ZD:中断"），则根据测试点描述按以下通用模板自行识别中断展开方向：

```
ZD 通用降级展开模板：
├── 涉及网络请求 → ZD-1:操作过程中断网后恢复
├── 涉及加载/处理过程 → ZD-2:操作过程中杀进程后重启
├── 涉及用户操作流程 → ZD-3:操作过程中切后台后恢复
├── 涉及异步等待 → ZD-4:操作超时后重试
├── 涉及时间相关逻辑 → ZD-5:操作跨越时间临界点
└── 涉及长耗时操作 → ZD-6:持续弱网导致超时中断后恢复
```

**覆盖率检查**（生成完用例后执行）：
```
□ 逐个检查适用分类包含ZD的测试点
□ 每个测试点至少有1条ZD用例覆盖（数量标准参见 `_shared_conventions.md §11`）
□ 未覆盖的测试点需补充用例或说明原因
```

### 步骤2：识别需要中断测试的场景

**需要 ZD 用例的场景：**
```
□ 网络请求类：创建、加入、保存、加载、刷新、验证
□ 异步操作类：加载中、处理中、等待中
□ 数据同步类：状态同步、数据更新、信息保存
□ 持久状态类：房间状态、游戏进度、用户设置
□ 时间边界类：操作跨越活动开始/结束时间、跨天/跨周期、定时任务触发时刻
□ 持续弱网类：弱网环境持续超过阈值（如30s），导致请求超时后的重试和状态恢复
```

## ZD 中断类型清单（7 类）

| 中断类型 | 触发方式 | 适用场景 |
|----------|----------|----------|
| ZD-1 网络中断重连 | 操作过程中断开网络，然后恢复 | 创建/加入/保存/加载等网络操作 |
| ZD-2 进程中断重启 | 操作过程中杀进程，重新启动 | 游戏中、加载中、操作执行中 |
| ZD-3 切换中断 | 操作过程中切换到后台/其他应用 | 输入过程中、加载过程中 |
| ZD-4 超时恢复 | 操作超时后重试 | 网络请求超时、等待响应超时 |
| ZD-5 时间边界穿越 | 操作跨越时间临界点（跨天/活动开始结束/定时任务触发时刻） | 限时活动、定时上下架、跨天结算、签到 |
| ZD-6 持续弱网中断 | 弱网环境持续超过阈值（如30s）导致操作超时中断 | 长耗时请求（上传/下载/批量操作）、实时同步 |

**ZD-5 时间边界穿越用例模板**：
```
1. 在{时间临界点}前开始执行{操作}
2. 操作执行期间跨越{时间边界}（如活动结束时间、跨天0:00）
3. 操作完成时检查结果
预期：{时间边界前的逻辑} or {时间边界后的逻辑}，无数据异常
```

**ZD-6 持续弱网中断用例模板**：
```
1. 在弱网环境（如限速50KB/s）下执行{操作}
2. 操作持续{N}秒未完成，触发超时
3. 网络恢复正常后重试
预期：超时有明确提示；重试后操作正常完成，数据无重复/丢失
```

**ZD-5/ZD-6 触发规则**：
- ZD-5：当需求涉及"限时""定时""活动周期""有效期""跨天"等时间相关逻辑时触发
- ZD-6：当需求涉及"上传""下载""批量""同步""长连接"等长耗时操作时触发

---

## 🚨 ZD 用例特殊规范

**操作步骤必须包含以下三段：**
1. 开始执行某操作
2. 在操作过程中触发中断（**必须明确中断时机**）
3. 恢复/重连/重启

**预期结果必须说明：**
- 中断时的表现（错误提示、状态保存等）
- 恢复后的状态（数据同步、状态恢复等）

**操作步骤模板：**
```
1. 执行{操作}
2. 在{操作}过程中{中断方式}（明确中断时机）
3. {恢复动作}
预期：{中断时表现}；{恢复后状态}
```

## 质量检查点

```
□ 创建类操作有中断用例：创建房间、创建xxx
□ 加入类操作有中断用例：加入房间、进入xxx
□ 保存类操作有中断用例：保存设置、修改信息
□ 加载类操作有中断用例：加载列表、刷新数据
□ 操作步骤包含"开始→触发中断时机→恢复"三段
□ 中断时机明确（操作开始时/进行中/即将完成时）
□ 恢复后状态验证：数据同步 + 状态恢复
□ 若某测试点在ZD分类下只有1条用例，检查展开说明是否暗示多种中断场景
□ 🚨 时间边界穿越：涉及限时/定时/活动周期的功能是否生成了ZD-5用例
□ 🚨 持续弱网：涉及上传/下载/批量/长耗时操作的功能是否生成了ZD-6用例
□ 🚨 应用崩溃：涉及事务性操作（支付/保存/提交）的功能是否生成了ZD-7用例
```

## JSONL 输出格式（append 模式）

将生成的每条用例逐行 append 到 `测试用例_模块/{模块名}.jsonl`（UTF-8 无 BOM）：

```python
import json
from pathlib import Path

out_file = Path(archive_dir) / "测试用例_模块" / f"{module_name}.jsonl"
out_file.parent.mkdir(parents=True, exist_ok=True)
with open(out_file, "a", encoding="utf-8") as f:      # 硬约束：mode='a'
    for case in cases:
        f.write(json.dumps(case, ensure_ascii=False) + "\n")
```

**JSONL 示例**：
```jsonl
{"submodule":"创建房间","feature_point":"玩家在游戏主页面创建新房间，支持公开/密码两种模式","testpoint":"验证创建房间功能","case_desc":"创建过程中网络中断后恢复","precondition":"网络正常，已进入创建页面","steps":"1.输入房间名\n2.点击创建按钮\n3.提交瞬间断网\n4.30秒后恢复网络","expected":"1.文字显示\n2.请求发送\n3.提示网络异常\n4.可重试创建，历史输入保留","category":"ZD"}
```

**字段规范**：
- **必填字段**：`submodule / feature_point / testpoint / case_desc / precondition / steps / expected / category`
- **`category` 只能填 `ZD`**（本 skill 负责的分类）
- **`module` 可省略**：由渲染层用文件名兜底
- **`feature_point` 必填**：值 = 测试点表格**第 2 列**「功能点描述」；**禁止留空、禁止依赖渲染层反查**
- **`testpoint` 与拆分器输出保持一致**：不重命名、不重排
- **多步骤用 `\n` 换行**（禁 `<br>`）
- 详细规范参见 `_shared_conventions.md §8.3`

## 注意事项

1. **只生成 ZD 分类的用例**
2. 注意区分 ZD 和 YC 的边界：ZD 是操作过程中被中断，YC 是异常状态下的操作
3. 中断时机要明确（操作中、操作后）
4. 恢复后的预期状态要具体
5. **必须使用 `open(mode='a')` 追加 JSONL**，禁止 `write_to_file` 覆盖已有文件；禁止 `replace_in_file` 修改 JSONL
6. 保持模块和子模块命名一致性
