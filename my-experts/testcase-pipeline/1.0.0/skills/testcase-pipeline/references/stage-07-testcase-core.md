# 核心用例生成 Skill

## 🚨 前置步骤（必须最先执行）

**在生成任何用例之前，必须加载共享规范 skill：**

```
use_skill: testcase-conventions
# 加载后按 SKILL.md §二加载策略读取（弱基座回落）
read_file: references/_shared_conventions.md
```

该文件包含：8列格式规范、分类定义、6条撰写规范、UI排除规则、数值具体化规范、追加工具约束。**以下所有步骤均在遵守共享规范的前提下执行。**

---

## 🚨 最高优先级约束

**本 Skill 只负责生成 HX（核心用例）和 FHX（非核心用例）两种分类。**

- ✅ 允许的分类：HX、FHX
- ❌ 禁止的分类：BL、BJ、YC、ZD（这些由其他 Skill 负责）

---

## 核心原则：一个测试点展开为多条用例

```
示例：测试点「验证创建房间功能」→ 展开为多条 HX/FHX 用例：
├─ 用例1：创建无密码房间（HX）
├─ 用例2：创建有密码房间（HX）
├─ 用例3：修改房间名后保存（FHX）
├─ 用例4：修改密码后保存（FHX）
└─ 用例5：取消创建返回（FHX）
```

---

## 执行流程

### 步骤1：读取测试点六列表格（强制）

从 `testpoint-splitter` 输出的六列表格中获取测试点列表，**重点关注「适用分类」「展开说明」「功能点描述」三列**。

**目的**：
- 通过「适用分类」和「展开说明」了解每个测试点还需要哪些分类的用例，在设计 HX/FHX 用例时为其他分类用例预留自然衔接点
- 通过「功能点描述」直接获取本测试点所属子模块的功能说明，写入 JSONL 的 `feature_point` 字段（**无需再读 功能点列表.md**）

**示例**：
```
测试点：验证创建房间功能（适用分类：HX,FHX,BJ,YC,FCG,ZD,BL）
展开说明：HX:正常创建流程; FHX:已有房间时再创建; BJ:房间名空值/临界/超限; YC:断网时创建/弱网提交; ZD:创建过程中网络中断恢复; BL:中文/英文/特殊字符房间名
功能点描述：玩家在游戏主页面创建新房间，支持公开/密码两种模式

HX用例设计时的衔接考虑：
- 操作步骤包含"输入房间名"→ 为BJ用例（名称边界）提供衔接
- 操作步骤包含"点击创建按钮"→ 为YC用例（断网创建）提供衔接
- 前提条件包含"网络正常"→ 为YC/ZD用例（断网场景）提供对比
- JSONL 输出时 feature_point 字段直接填"玩家在游戏主页面创建新房间，支持公开/密码两种模式"
```

**🚨 降级展开逻辑（当展开说明缺失或笼统时）**：

如果某测试点的「展开说明」列为空、仅有分类标签（如"HX:正常"）、或过于笼统（如"HX:核心"），则按以下通用模板自行识别 HX/FHX 展开方向：

```
HX 通用展开模板：
├── 功能是否正常启动/打开 → 1条用例
├── 核心操作的主路径执行 → 1条用例
├── 操作结果是否符合预期 → 1条用例（若与主路径用例可合并则合并）
├── 涉及输入框 → 正常输入并提交 → 1条用例
└── 涉及列表/数据展示 → 正常加载展示 → 1条用例

FHX 通用展开模板：
├── 可选路径/非必经操作 → 1条用例
├── 特定前提条件下执行（如已有同名数据时再操作） → 1条用例
└── 取消/返回/中途退出 → 1条用例
```

**强制要求**：
- 只为适用分类包含 HX 或 FHX 的测试点生成用例
- 展开说明暗示多种子场景时，**必须为每种子场景生成独立用例**，禁止合并为1条

### 步骤2：筛选适用测试点

- 适用分类含 HX → 必须生成 HX 用例
- 适用分类含 FHX → 必须生成 FHX 用例
- 纯展示类测试点（只有HX）→ 至少生成1条 HX 用例

**🚨 HX 最低展开数约束**：

| 测试点类型 | 最低用例数 | 说明 |
|-----------|:---------:|------|
| 非纯展示型（有交互/输入/网络请求/状态变化） | **≥ 2条** | 至少覆盖主路径 + 1个变体 |
| 纯展示型 | ≥ 1条 | 仅验证可见性即可 |

**「纯展示型」判定条件**（必须同时满足以下全部条件）：
1. 仅验证某UI元素的**可见性/存在性**（如"验证XX入口显示"）
2. **无任何用户交互**：无输入、无点击操作、无滑动
3. **无网络请求**：不触发后端接口调用
4. **无状态变化**：不涉及数据增删改、状态流转

**示例**：
- ✅ 纯展示型：`验证联机入口显示` → 只需1条用例
- ❌ 非纯展示型：`验证房间列表展示` → 有网络请求加载数据，至少2条用例
- ❌ 非纯展示型：`验证创建房间功能` → 有输入+点击+网络请求，至少2条用例

### 步骤3：用例设计策略

#### HX 用例设计要点

```
□ 功能是否正常启动/打开
□ 核心操作是否成功执行
□ 操作结果是否符合预期
□ 数据显示是否正确（非样式）
□ 状态切换是否正确
```

**HX 用例示例：**

| 测试点 | 用例描述 | 分类 |
|--------|----------|------|
| 验证创建房间功能 | 正常创建无密码房间 | HX |
| 验证创建房间功能 | 创建带密码房间 | HX |
| 验证加入房间功能 | 正常加入可用房间 | HX |

#### FHX 用例设计要点

```
□ 可选功能是否正常工作
□ 非必经路径是否可用
□ 特定条件下的功能表现
□ 次要操作的正确性
```

**FHX 用例示例：**

| 测试点 | 用例描述 | 分类 |
|--------|----------|------|
| 验证创建房间功能 | 已在房间内时创建新房间 | FHX |
| 验证搜索房间功能 | 查看搜索历史记录 | FHX |

### 步骤4：通用组件识别

扫描测试点，涉及通用UI组件时读取参考文件：

| 组件类型 | 识别关键词 | 参考文件 |
|----------|------------|----------|
| 文字输入框 | 输入框、搜索框、密码、房间名 | `references/文字输入框通用用例.md` |

### 步骤5：输出 JSONL（append 模式）

将生成的每条用例逐行 append 到 `测试用例_模块/{模块名}.jsonl`（UTF-8 无 BOM）：

```python
import json
from pathlib import Path

out_file = Path(archive_dir) / "测试用例_模块" / f"{module_name}.jsonl"
out_file.parent.mkdir(parents=True, exist_ok=True)
with open(out_file, "a", encoding="utf-8") as f:      # 硬约束：mode='a'，禁 write_to_file 覆盖
    for case in cases:
        f.write(json.dumps(case, ensure_ascii=False) + "\n")
```

**JSONL 示例**（每行一个 JSON 对象）：

```jsonl
{"submodule":"创建房间","feature_point":"玩家在游戏主页面创建新房间，支持公开/密码两种模式","testpoint":"验证创建房间功能","case_desc":"正常创建无密码房间","precondition":"已进入创建房间页面","steps":"1.输入房间名\n2.点击创建按钮","expected":"1.文字显示在输入框\n2.房间创建成功","category":"HX"}
{"submodule":"创建房间","feature_point":"玩家在游戏主页面创建新房间，支持公开/密码两种模式","testpoint":"验证创建房间功能","case_desc":"已在房间内时创建新房间","precondition":"玩家已在房间内","steps":"1.点击创建按钮","expected":"1.提示已在房间中","category":"FHX"}
```

**字段规范**（本 skill 输出的 JSON 对象）：
- **必填字段**：`submodule / feature_point / testpoint / case_desc / precondition / steps / expected / category`
- **`category` 只能填 `HX` 或 `FHX`**（本 skill 负责的分类）
- **`module` 可省略**：由渲染层用文件名兜底（写了会被文件名覆盖）
- **`feature_point` 必填**：值 = 测试点表格**第 2 列**「功能点描述」；同一子模块下所有用例该字段值完全相同；**禁止留空、禁止依赖渲染层反查**
- **`testpoint` 与拆分器输出保持一致**：不重命名、不重排
- **多步骤用 `\n` 换行**（禁 `<br>`）
- 详细规范参见 `_shared_conventions.md §8.3`

## 质量检查点

```
□ 所有核心功能测试点都有 HX 用例覆盖
□ HX 用例验证功能的正向流程
□ 前提条件清晰、可达成
□ 操作步骤明确、可执行
□ 预期结果具体、可验证
□ 可选功能有 FHX 覆盖，且不与 HX 重复
□ 所有数量/长度/时间数值已具体化（无"若干"等模糊词）
□🚨 非纯展示型测试点至少有2条 HX/FHX 用例（若只有1条，需确认是否为纯展示型；数量标准参见`_shared_conventions.md §11`）
□ 🚨 展开说明中暗示的每个子场景都有独立用例覆盖
```

## 注意事项

1. **只生成 HX 和 FHX 分类的用例**
2. 边界、异常、中断、遍历场景由其他 Skill 负责
3. 输出 JSONL 格式（append 追加），按模块分文件存储到 `测试用例_模块/` 目录
4. 保持模块和子模块命名一致性
