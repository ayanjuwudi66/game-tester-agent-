# 功能点拆分 Skill

## 功能概述
此skill将整理后的需求文档进行分析，拆分为独立、可测试的功能点列表。

## 使用场景
在 `requirement-organizer` skill完成需求整理后，调用此skill拆分功能点。

## 功能点定义
一个**功能点**是指：
- 用户可感知的独立功能单元
- 具有明确的输入和输出
- 可以独立验证的功能项
- 具有独立的业务价值

## 执行流程

### 步骤1：接收需求文档和归档信息
从 `requirement-organizer` 的输出中获取结构化的需求内容。
从 `file-scanner` 的输出中获取归档目录信息。

### 步骤2：功能点识别策略

#### 2.1 按用户操作拆分
- 每个用户可执行的独立操作作为一个功能点
- 例如：点击、输入、选择、提交等

#### 2.2 按业务流程拆分
- 业务流程中的每个关键节点作为一个功能点
- 例如：登录、浏览、加购、下单、支付

#### 2.3 按页面/模块拆分
- 每个页面或模块的核心功能作为功能点
- 例如：首页展示、列表页、详情页

#### 2.4 按数据操作拆分
- 增删改查操作分别作为独立功能点
- 例如：创建订单、修改地址、删除记录

#### 2.5 关键数值识别（为下游测试点/用例做准备）

**重要：在功能点描述中，必须明确记录以下数值信息，便于后续 testpoint-splitter 和 testcase-boundary 使用。**

| 数值类型 | 示例 | 记录位置 |
|----------|------|----------|
| 长度限制 | 房间名最多10个字符 | 关联规则/预期行为 |
| 数量上限 | 列表最多显示8条 | 关联规则/预期行为 |
| 位数要求 | 密码必须6位 | 关联规则 |
| 时长限制 | 气泡显示3秒后消失 | 预期行为 |
| 字符类型限制 | 只允许中文/英文/数字 | 关联规则 |

**示例**：
```markdown
**关联规则**
- 房间名长度限制：1-10个字符
- 允许输入：中文、英文、数字
- 禁止输入：特殊符号、空格
```

#### 2.6 场景法辅助识别

**当需求文档中包含流程图时，使用场景法识别功能点：**

1. **识别流程图中的分支节点** - 每个判断分支可能对应一个或多个功能点
2. **识别流程图中的操作节点** - 每个用户操作节点对应一个功能点
3. **识别流程图中的状态节点** - 状态切换相关的功能作为功能点

**场景法识别示例**（基于流程图）：
```
流程分支：[房间数量<8?]
├─ Yes → 功能点：正常显示房间列表
└─ No  → 功能点：显示滚动列表

流程分支：[是否设置密码?]
├─ Yes → 功能点：密码设置弹窗
└─ No  → 功能点：直接创建公开房间
```

**注意**：场景法识别的功能点需要在后续测试点拆分阶段进一步展开为边界用例（BJ）。

#### 2.7 配置字段映射规则（如上游输出包含「第四章 配置表数据」）

**当 `requirement-organizer` 输出中包含「第四章 配置表数据」时，按以下4条规则将配置字段映射为测试方向：**

| 规则编号 | 触发条件 | 映射动作 | 示例 |
|----------|----------|----------|------|
| M1-枚举遍历 | 字段类型=枚举 | 为每个枚举值生成一个测试方向；若枚举值影响UI展示差异，在该测试方向中标注"需验证UI差异" | 商品状态(上架/下架/预售)→3个测试方向 |
| M2-数值边界 | 字段类型=数值且有取值范围 | 生成边界值测试方向（下限/上限/越界）；若文档指明业务上限，同时标注业务上限值 | 库存0~99999→边界测试方向(0/99999/100000) |
| M3-必填容错 | 是否必填=是 | 生成"必填字段为空提交"测试方向 | 商品名称必填→空值提交验证 |
| M4-条件联动 | 生效条件列非空 或 关联字段列非空 | 生成"条件满足/不满足时字段行为"测试方向 | 预售商品→上架时间字段生效验证 |

**规则说明**：
- 同一字段可能同时命中多条规则（如枚举+必填），各规则产生的测试方向不重复
- M4为按需规则：当上游「第四章 配置表数据」的"生效条件"或"关联字段"列为空时，不触发此规则
- 若需求无配置字段（上游标注"无"），跳过本节

**配置字段覆盖检查表**（附在功能点列表末尾）：

```markdown
### 配置字段覆盖检查表

| 字段名 | M1枚举遍历 | M2数值边界 | M3必填容错 | M4条件联动 | 对应功能点ID |
|--------|:----------:|:----------:|:----------:|:----------:|-------------|
| {字段名} | ✓/— | ✓/— | ✓/— | ✓/— | F00x |
```

> 此检查表用于下游 testpoint-splitter 验证配置字段是否被完整覆盖。

### 步骤3：功能点分类

将识别的功能点按以下维度分类：

| 分类维度 | 说明 |
|----------|------|
| 模块归属 | 功能点所属的业务模块 |
| 功能类型 | 核心功能/辅助功能/配置功能 |
| 优先级 | P0(必须)/P1(重要)/P2(一般) |
| 复杂度 | 高/中/低 |

### 步骤4：功能点描述规范

每个功能点包含以下信息：

```markdown
### 功能点: {功能点ID} - {功能点名称}

**基本信息**
| 属性 | 值 |
|------|-----|
| 所属模块 | {模块名} |
| 功能类型 | {核心/辅助/配置} |
| 优先级 | {P0/P1/P2} |
| 复杂度 | {高/中/低} |

**功能描述**
{一句话描述功能点的作用}

**前置条件**
- {条件1}
- {条件2}

**触发方式**
{如何触发此功能}

**预期行为**
{功能执行后的预期结果}

**关联规则**
- {业务规则ID}: {规则描述}

**UI要素**
- {相关的UI元素}

**异常场景**
- {可能的异常情况}

**关联配置字段**（如有，来自「第四章 配置表数据」）
- {字段名}: {字段类型}, 取值范围{范围}, 命中规则{M1/M2/M3/M4}
```

### 步骤5：输出功能点清单

**⚠️ 重要：功能点列表必须使用下方"标准输出格式"，禁止使用简略表格。**

#### 标准输出格式（必须严格遵循）

```markdown
# 功能点列表：{需求名称}

> 功能点是可独立测试的最小业务单元。本列表定义了模块顺序，后续用例按此顺序聚合。

## 模块总览

| # | 模块 | 子模块数 | 说明 |
|---|------|---------|------|
| 1 | {模块名1} | {子模块数} | {一句话说明} |
| 2 | {模块名2} | {子模块数} | {一句话说明} |
| ... | ... | ... | ... |

---

## 模块 1：{模块名1}

### 1.1 {子模块名称}
- **描述**：{该功能点做什么，一两句话}
- **来源**：{引用需求原文段落、配置表字段、或图片名 image_X}
- **关键点**：{验证时需要关注的核心要点，用分号分隔}

### 1.2 {子模块名称}
- **描述**：{该功能点做什么}
- **来源**：{引用来源}
- **关键点**：{核心要点}

---

## 模块 2：{模块名2}

### 2.1 {子模块名称}
- **描述**：{...}
- **来源**：{...}
- **关键点**：{...}

（以此类推）
```

#### 输出格式核心要求

| 要求项 | 说明 |
|--------|------|
| 模块总览表 | 必须在开头列出所有模块编号、名称、子模块数、一句话说明 |
| 子模块编号 | 使用"模块号.子编号"格式（如 1.1, 1.2, 2.1） |
| 三要素必填 | 每个子模块必须包含**描述**、**来源**、**关键点**三个字段 |
| 来源引用 | 来源必须明确引用需求原文、配置表字段名、或图片编号（如"图 image_3"） |
| 关键点 | 关键点是测试验证的核心方向，简明列出正/反向验证点 |
| 模块间分隔 | 模块之间用 `---` 分隔 |

#### ❌ 禁止的简略格式

以下格式**不允许使用**（过于简略，缺乏来源和验证方向）：

```markdown
## 模块一：XXX

| 功能点 | 描述 |
|--------|------|
| 某功能 | 简单描述 |
```

#### 格式对比示例

❌ **错误示例**（过于简略）：
```markdown
| 功能点 | 描述 |
|--------|------|
| 商店入口 | 点击玩家金币栏进入商店 |
```

✅ **正确示例**（标准格式）：
```markdown
### 1.2 金币栏入口
- **描述**：点击游戏主界面的玩家金币栏进入商店
- **来源**：一、1.1 活动入口：点击玩家金币栏进入商店
- **关键点**：金币栏可点击；点击后跳转商店界面
```

## 拆分原则

### 1. 单一职责原则
- 每个功能点只描述一个独立的功能
- 避免将多个功能混在一起

### 2. 可测试原则
- 功能点必须可以通过测试验证
- 有明确的验证标准

### 3. 完整性原则
- 确保覆盖需求文档中的所有功能
- 不遗漏隐含的功能需求

### 4. 粒度适中原则
- 不要拆分得过细（如：点击按钮）
- 不要保持过粗（如：完成购物流程）

## 输出文件归档
功能点列表需要保存到归档目录：

文件路径：`{归档目录}/功能点列表.md`

示例：`output/G089-MS5-首页推荐功能_202602161430/功能点列表.md`

## 注意事项
1. 功能点ID需要全局唯一
2. 保持功能点命名的一致性和规范性
3. **功能点列表必须保存到归档目录**
4. 功能点拆分结果和归档信息需要传递给 `testpoint-splitter` skill进行测试点拆分
